# **1\. Загальний опис проєкту**

Nobel ITBS створює новий корпоративний освітній сайт на власному технологічному стеку замість чинного сайту, розробленого на конструкторі.

Новий продукт має об’єднати три основні функції:

1. презентацію Nobel ITBS як чеської компанії у сфері професійної освіти дорослих;  
2. каталог освітніх програм із переходом користувача у відповідну воронку Leeloo;  
3. систему реєстрації та перевірки дипломів, сертифікатів та інших освітніх документів через QR-код і унікальний verification token.

Новий сайт не є редизайном чинного сайту. Дизайн, інформаційна архітектура, програмний код і адміністративна система створюються з нуля.

Чинний сайт використовується тільки як джерело:

* підтверджених фактів про компанію;  
* окремих назв і описів програм;  
* базового позиціонування;  
* контактних даних;  
* матеріалів, які Product Owner окремо схвалить для перенесення.

---

# **2\. Проблема, яку розв’язує продукт**

Чинний сайт має системні обмеження:

* залежить від конструктора;  
* не має повноцінної бази програм;  
* не дозволяє централізовано управляти освітнім контентом;  
* не має реєстру виданих документів;  
* не підтримує перевірку документів через QR-код;  
* не має адміністративного кабінету;  
* не забезпечує єдиного стандарту сторінок програм;  
* не підтримує подальші інтеграції з Moodle, Leeloo, цифровими credentials та іншими сервісами;  
* не відповідає запланованому масштабу Nobel ITBS.

Через це сайт не може виконувати роль повноцінної цифрової платформи компанії.

# **3\. Бізнес-мета**

## **3.1. Головна мета**

Створити офіційну цифрову платформу Nobel ITBS, яка:

* формує довіру до компанії;  
* презентує освітні програми;  
* переводить користувача зі сторінки програми у відповідну воронку Leeloo;  
* дозволяє незалежно перевірити справжність виданих документів.

## **3.2. Основна конверсійна дія**

Головна конверсія сайту:

> **Перехід користувача зі сторінки програми у відповідну воронку Leeloo.**

Основні CTA:

* Apply Now;  
* Join the Programme;  
* Get Programme Details;  
* Подати заявку;  
* Приєднатися до програми;  
* Отримати детальну інформацію.

Для кожної програми або конкретного запуску зберігається Leeloo URL.

Пріоритет використання URL:

1. якщо Programme Run має власний `leeloo_url`, використовується він;  
2. якщо Programme Run не має URL, використовується `default_leeloo_url` програми;  
3. якщо обидва URL відсутні, користувач бачить резервний CTA для звернення.

## **3.3. Другорядні цілі**

Новий сайт повинен:

* системно представляти напрями діяльності Nobel ITBS;  
* підвищувати цінність дипломів і сертифікатів через офіційний реєстр;  
* створювати професійний міжнародний образ компанії;  
* підтримувати українську та міжнародну аудиторію;  
* забезпечувати централізоване управління програмами;  
* скоротити залежність від програміста при щоденному оновленні даних;  
* створити основу для наступних інтеграцій;  
* забезпечити масштабування кількості програм і документів;  
* відстежувати переходи користувачів у Leeloo.

# **8\. Основні користувацькі сценарії**

## **8.1. Вибір програми**

**Маршрут:**

Головна → Programmes → Сторінка програми → CTA → Leeloo

**Очікуваний результат:**

Користувач знаходить програму, розуміє її зміст і переходить у відповідну воронку Leeloo.

## **8.2. Перевірка документа через QR-код**

**Маршрут:**

Сканування QR-коду → Сторінка перевірки → Результат

**Очікуваний результат:**

Користувач одразу бачить статус і основні дані документа.

## **8.3. Ручна перевірка документа**

**Маршрут:**

Verify Credential → Одне поле «Document number or verification code» → Результат

Система автоматично визначає, який тип ідентифікатора введено:

* публічний номер документа;  
* verification code.

QR-код завжди використовує verification token.

**Очікуваний результат:**

Користувач може перевірити документ без QR-коду.

## **8.4. Створення документа адміністратором**

**Маршрут:**

Адмінпанель → Learner → Programme → New Credential → QR

**Очікуваний результат:**

Документ з’являється у реєстрі й отримує публічну сторінку перевірки.

## **8.5. Анулювання документа**

**Маршрут:**

Адмінпанель → Credential → Change Status → Revoked

**Очікуваний результат:**

На публічній сторінці відображається статус анулювання.

## **8.6. Перевидача документа**

**Маршрут:**

Адмінпанель → Credential → Reissue → New Credential

**Очікуваний результат:**

Старий документ отримує статус Reissued, новий — Valid. Між записами зберігається зв’язок.

## **8.7. Звернення організації або партнера**

**Маршрут:**

For Organisations або Partners → Contact CTA → Форма або визначений канал

**Очікуваний результат:**

Компанія отримує запит на партнерство або корпоративну програму.

Базові типи:

* Certificate;  
* Professional Development Certificate;  
* Professional Development Diploma;  
* MINI-MBA Diploma;  
* CPD Certificate;  
* Certificate Supplement;  
* Transcript;

Для кожного типу визначаються:

* назва;

## **10.8. Статуси документа**

Release 1 підтримує:

* Pending;  
* Valid;  
* Revoked;  
* Reissued;  
* Expired.

### **Публічна логіка Pending**

Pending credential не показує персональні або змістові дані документа.

Публічний результат:

> **This credential is not yet active.**

До моменту активації Pending credential не вважається підтвердженим документом.

## **10.9. Snapshot даних credential**

При створенні документа система зберігає snapshot даних, які фактично стосуються виданого документа.

Snapshot включає:

# **18\. Критерії приймання Release 1**

## **18.1. Публічний сайт**

* усі затверджені сторінки доступні;  
* сайт працює на desktop, tablet і mobile;  
* українська й англійська версії функціонують;  
* немає критичних broken links;  
* старі основні URL перенаправляються;  
* CTA ведуть у правильну воронку Leeloo;  
* UTM-параметри передаються;  
* SEO metadata заповнені;  
* сайт розгорнуто на основному домені.

## **18.2. Каталог**

* програми завантажуються з бази;  
* програми можна фільтрувати за Must-have критеріями;  
* кожна програма має окрему сторінку;  
* адміністратор може створити та відредагувати програму без зміни коду;  
* відсутність опційних полів не ламає сторінку.

## **18.3. Leeloo**

* Programme Run URL має пріоритет над Programme URL;  
* CTA відкриває правильну воронку;  
* натискання CTA фіксується в аналітиці;  
* UTM-параметри не губляться;  
* якщо обидва URL відсутні, користувач бачить резервну дію.

## **18.4. Credential verification**

* адміністратор може створити credential;  
* система створює унікальний verification token;  
* система створює QR-код;  
* QR відкриває правильний credential;  
* одне поле ручного пошуку приймає document number або verification code;  
* статус відображається правильно;  
* Pending не розкриває персональних даних;  
* неіснуючий код не розкриває зайвих даних;  
* старий документ після перевидачі показує відповідний статус;  
* публічні й приватні поля розділені;  
* snapshot не змінюється після редагування Programme, Learner або Partner.

## **18.5. Адмінпанель**

* доступ можливий тільки після авторизації;  
* ролі працюють відповідно до дозволів;  
* Credential Manager не може змінювати Credential Types;  
* критичні зміни записуються в audit log;  
* адміністратор може управляти програмами, Programme Runs, learners і credentials;  
* зміна статусу відображається на публічній сторінці.

## **18.6. Partners**

* сторінка показує тільки підтверджених партнерів;  
* для кожного партнера вказано роль;  
* партнер пов’язаний із відповідними програмами;  
* сторінка підтримує формування довіри;  
* CTA веде до сценарію співпраці.

## **18.7. Технічна якість**

* production environment відокремлений від development;  
* секретні ключі не зберігаються у frontend-коді;  
* Supabase RLS налаштовано;  
* приватні PDF, якщо використовуються, не доступні за відкритим URL;  
* створено резервну копію перед запуском;  
* критичні сценарії протестовані;  
* публічні дані відокремлені від внутрішніх.

# **22\. Основні ризики**

## **Scope creep**

Ризик постійного додавання функцій до Release 1\.

**Рішення:** нові функції після затвердження Brief потрапляють у backlog.

## **Незатверджений контент**

Розробка може блокуватися через відсутність готових текстів і даних програм.

**Рішення:** паралельна контентна матриця з відповідальними та статусами.

## **Надмірна складність адмінпанелі**

Спроба створити повноцінну CMS різко збільшить обсяг робіт.

**Рішення:** у Release 1 управляти лише структурованими даними.

## **Неправильна модель credential**

Помилки в архітектурі реєстру складно виправляти після масової видачі документів.

**Рішення:** до коду затвердити Credential Type, формат номера, token, snapshot, статуси, перевидачу й публічні поля.

## **Залежність від Leeloo**

Якщо зовнішня воронка не працює, основна конверсія сайту зупиняється.

**Рішення:** резервний CTA, перевірка URL і моніторинг переходів.

## **Неповні дані партнерів**

Сторінка Partners може знижувати довіру, якщо ролі партнерів описані нечітко або непослідовно.

**Рішення:** для кожного партнера затвердити роль, програми та документи до публікації.

## **Мовна складність**

Дві мови збільшують обсяг дизайну, контенту й QA.

**Рішення:** EN та UA запускаються разом; Czech додається окремим етапом.

## **Залежність від Codex**

Без чітких acceptance criteria Codex може самостійно ухвалювати продуктові рішення.

**Рішення:** кожна задача Codex формується як окремий ticket із контекстом, обмеженнями й критеріями приймання.

# **24\. Підсумок Release 1**

Перший реліз Nobel ITBS — це:

> Новий двомовний корпоративний освітній сайт із каталогом програм, переходом заявників у Leeloo, trust-page партнерів, структурованою адміністративною системою та офіційною перевіркою дипломів і сертифікатів через QR-код.

Release 1 повинен довести чотири ключові можливості:

1. Nobel ITBS може самостійно управляти програмами та їх запусками.  
2. Користувач може знайти програму й перейти у відповідну воронку Leeloo.  
3. Nobel ITBS може зареєструвати виданий документ.  
4. Третя сторона може перевірити справжність документа через QR-код або verification code.
