# QA-003 MFA Tests

Date: 2026-08-10  
Scope: sensitive actions blocked without MFA/AAL2

## Summary

QA-003 is complete at the current dev level. The aggregate MFA suite covers all four application roles, AAL1/AAL2 interpretation, active-profile and multi-role MFA resolution, protected RLS policies, user/role management, learners, contacts, site settings, content operations for MFA-required roles, credential lifecycle functions, PDF operations, and server route guards.

A fresh dev Owner password session was confirmed as `aal1` with a verified TOTP factor available for upgrade to `aal2`. That authenticated session was then denied by all 11 tested sensitive admin routes with HTTP `403` and an explicit `MFA/AAL2` message. No records or configuration values were changed.

## MFA Contract

| Role | Default MFA requirement | AAL1 sensitive access | AAL2 authorized access evidence |
| --- | --- | --- | --- |
| Owner | Required | Denied | Existing Owner admin/browser QA passed |
| Super Admin | Required | Denied | Stage 2–4 live role QA passed |
| Content Manager | Optional | Permitted for editorial work when the profile does not independently require MFA | Existing content CRUD QA passed |
| Credential Manager | Required | Denied | Stage 2–4 and credential-module live role QA passed |

For a user with multiple roles, any assigned MFA-required role makes the session MFA-required. The server checks both `profile.mfa_required` and the assigned role set; the database assignment trigger also forces `mfa_required` when Owner, Super Admin, or Credential Manager is assigned.

## Security Notes

- AAL is read from the verified Supabase access-token claim, not client-submitted form data.
- Application roles are resolved from `user_profiles` and `user_roles`, not user-editable metadata.
- Sensitive routes establish the active actor and MFA context before protected data access.
- Database RLS/functions remain a second enforcement layer behind server guards.
- No TOTP code, MFA secret, factor identifier, access token, password, or service-role key was printed or persisted by the test.
- The fresh test session was local to the non-persistent test client and was signed out after verification.
