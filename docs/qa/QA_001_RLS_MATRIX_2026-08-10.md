# QA-001 RLS Matrix

Date: 2026-08-10  
Scope: every Release 1 role and every protected public table

## Summary

QA-001 is implemented and accepted at the current dev level. One aggregate pgTAP suite now guards the complete authorization contract instead of relying only on ticket-by-ticket checks. It covers all 36 application tables in `public`, both server-only rate-limit tables in `internal`, the private credential Storage bucket, controlled RPC boundaries, the four-role model, MFA coupling, multi-role support, and Owner uniqueness.

The live anonymous boundary was re-run against the connected dev Supabase project and passed. Authenticated role behavior is supported by the earlier live module reports and is now protected against migration drift by the aggregate catalogue/policy assertions. No database data was created or changed during the live QA run.

## Role Matrix

| Actor | Public content | Programme/content mutation | Learner/contact/credential data | Sensitive workflow RPCs |
| --- | --- | --- | --- | --- |
| Anonymous | Published rows only | Denied | Denied | Denied; server API mediates public contact and verification |
| Content Manager | Read and edit approved content objects | Allowed by content policies | Denied | Denied |
| Credential Manager | Read programme references | Denied | Allowed after MFA | Allowed after MFA and function-level checks |
| Super Admin | Read and edit content | Allowed | Allowed after MFA | Allowed after MFA and function-level checks |
| Owner | Read and edit content | Allowed | Allowed after MFA | Allowed after MFA and function-level checks |

The role model remains multi-role: `user_roles` uses `(user_id, role)` as its primary key. The single active Owner guarantees remain enforced by the two partial unique indexes.

## Protected Object Inventory

- 36 application tables in `public` have both enabled and forced RLS.
- 18 tables expose an anonymous `SELECT` grant for published content/catalogue/settings data only.
- 18 private tables deny anonymous reads.
- Anonymous direct `INSERT`, `UPDATE`, and `DELETE` grants are absent from all public-schema tables.
- `internal.contact_submission_rate_limits` and `internal.credential_verification_rate_limits` are service-only.
- `private-credentials` remains a private Storage bucket without browser-object policies.
- Identity and audit tables have no direct authenticated table privileges or RLS policies; controlled server functions remain the access boundary.
